# Photowall commercial MVP assessment

Reviewed 2026-11-21 against `main` at `ac1d43b`. The product brief supplied for this review is the source for the commercial direction. The repository and its available branch history contain [operational notes](photowall-notes.md) and a [review of earlier branches](branch-review.md), but no standalone product brief or MVP plan. The [implementation plan](mvp-implementation-plan.md) records the working backlog from the available material.

## Product and code fit

The storefront stays live at `erik.roxen.com` initially. Loopia remains registrar, Cloudflare handles DNS and event hostnames, and free demos share infrastructure. Paid events cost 99 SEK for 24 hours or 129 SEK for 72 hours. The first release covers mobile photo upload, a live carousel and tiled wall, simple themes, host moderation, ZIP export, and automatic expiry and deletion. Video is out of scope.

| Requirement | Available on main | Work before commercial use |
| --- | --- | --- |
| Mobile browser upload | One multipart photo at a time, caption, optional upload PIN, uploads disabled by default. | Validate image content, limit resource use, and exercise the mobile flow on real devices. Keep JPG, PNG, GIF and WebP and the 10 MiB file limit. |
| Tiled wall and live carousel | Grid and masonry wall, swipe/keyboard viewer, fullscreen polling slideshow. Wall and slideshow poll every 15 and 10 seconds, respectively. | Verify updates across workers, private media, and performance at the event quota. The clients currently request up to 400 items. |
| Simple themes | Existing separate templates and stylesheets. | Add a small preset list using CSS variables, scoped by event. |
| Host moderation | Admin grid and PIN-protected delete. The admin page itself is public and list access follows viewer access. | Add host-only entry and session handling in commercial mode. Delete-based moderation is sufficient for the first release. |
| ZIP export | `/download` builds a temporary ZIP with originals, captions and an offline gallery in the app directory. It follows viewer access today. | Make commercial export host-only, bound generation and temporary space, and verify races with deletes and expiry. Decide how retained original metadata is disclosed. |
| Event isolation, expiry and deletion | Process-wide env/config, one upload directory and metadata index. `PHOTO_ROOT` supports browsing a different directory, with read-only defaults. | Add explicit writable runtime paths, event-scoped routing and credentials, a durable lifecycle record, expiry enforcement and a reconciler. |
| Storefront, payment and demos | Existing Caddy and Gunicorn/systemd examples for one app. | Add storefront, hosted checkout, verified fulfillment and host delivery. Give demos isolated storage and tighter limits on a shared runtime. |

Keep Flask, Pillow, Gunicorn, templates, static JavaScript, polling and filesystem storage for the first implementation steps. A writable runtime directory is enough to mount event data. Keep the existing library mode and filename-caption fallback. The old branches contain redirect-validation and upload UX ideas, and their review documents the library-mode regressions a wholesale merge would introduce. Multi-select can wait, and a future client can submit a series of single-file uploads. A frontend rewrite, WebSockets, per-event deployment repositories, and a managed database are unnecessary for this path. Start the lifecycle ledger on one durable host using Python's SQLite if approved for that task. Revisit replicated media storage only if the paid recovery gate requires it.

## Hosting decision

Keep temporary paid Machines as the leading candidate for a staging spike. They fit the current single-event process model and isolate per-event compute, disk and configuration. Run free demos on a shared service, starting with one resettable synthetic gallery with public viewing and uploads disabled. Keep the shared multi-event option open until both candidates have been measured with the same workload. The shared option is especially attractive if the existing host has measured spare capacity and reliable storage. Whichever option is selected, the storefront, checkout ledger and cleanup scheduler must survive the loss of any one event runtime.

| | Temporary Fly Machines | Shared multi-event Flask application |
| --- | --- | --- |
| Request and data isolation | Dedicated VM and volume per paid event, with one routing lookup per request. Shared networking still needs explicit access controls. | Resolve trusted host to immutable event ID on every route. Namespace media, credentials, sessions, quotas, caches, ZIP files and cleanup. Test cross-event access. |
| Capacity and outages | Pay per event while allocated, with a separate limit for concurrent events. Start capacity, volume placement and boot failures need automatic recovery. Loss of the volume host can affect one paid event. | Pay for warm capacity and add capacity at concurrency thresholds. A busy event can affect all events on the node. Deploys, disk exhaustion and node failure have a wider blast radius. |
| Operations | Keep a gateway and lifecycle controller, reconcile Machine and volume separately, and monitor provider/API failures and leaked spend. | Keep a gateway and lifecycle controller. Create and purge event directories and reconcile state. No Machine provisioning on the checkout path. |
| Growth | Pin an image version for each event. Reuse the same app and rolling image versions for new events. | Release once for the fleet. A single host and volume are the smallest baseline. Multiple nodes need a routing or storage strategy with explicit ownership of each event. |

### Provisioning feasibility

The documented Fly API supports volume create/list/get/delete and Machine create/list/get/wait/delete. A Machine can launch a pinned container image with a volume mount. The API's started state is followed by an application readiness check, including a writable mount. Fly private DNS can address a specific Machine by `<machine_id>.vm.<appname>.internal`. This supports a shared gateway that resolves an event to its own Machine and forwards requests over Fly private networking. Use a permanent Fly gateway in the selected region for the comparison, with event Machines in a precreated app without public ingress. Keep provisioning credentials in the controller. Check app-scoped token permissions and private-network isolation in staging. The same-origin guest URL should preserve paths, headers and request bodies, while inbound routing/forwarding headers are overwritten or ignored. Verify that only the gateway can reach protected backends. [Machines API](https://docs.fly.io/machines/api/machines-resource), [Volumes API](https://docs.fly.io/machines/api/volumes-resource), [Fly private networking](https://docs.fly.io/networking/private-networking), [Deploy token scope](https://docs.fly.io/flyctl/cmd/fly_tokens_create_deploy).

Use first-level hosts such as `<slug>.<event-domain>` on a zone delegated to Cloudflare. One proxied wildcard points at the gateway for either topology. Keep Loopia as registrar and coordinate nameserver/DNSSEC changes with existing records and services. The actual domain and access to the zone still need confirmation. Treat `erik.roxen.com` as the storefront origin and leave its DNS alone. Confirm edge certificate coverage and Full (strict) to a correctly configured origin, and restrict origin access. A DNS wildcard alone neither chooses the Machine nor supplies TLS coverage for deeper names. Reject unknown hosts and bypass content caches for commercial event routes. [Loopia nameservers](https://support.loopia.se/wiki/byt-namnservrar/), [Cloudflare wildcard records](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/), [Universal SSL coverage](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/), [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/).

Create the durable event record before contacting Fly, use deterministic resource labels and record provider IDs, then publish the route only after readiness. Serialize work per event. If the API times out after accepting a request, reconcile by event label and ID before retrying. For expiry, deny traffic first, drain or terminate bounded operations, remove the Machine, then explicitly delete the detached volume. Treat already-absent resources as success only after checking identity and scope. Retry with bounded backoff, reconcile orphan inventory and alert on overdue resources. A mounted Fly Volume is local to one server and is unreplicated. Its automatic snapshots are enabled by default and may remain after deleting the volume. Match any snapshot and restore design to the customer retention promise. For the synthetic spike, turn automatic snapshots off and verify the provider reports that setting. For launch, require a tested recovery path and a documented deletion deadline for all copies. [Fly Volumes](https://fly.io/volumes/), [Fly snapshot retention after deletion](https://fly.io/legal/security-questionnaire/).

**Evidence and limits.** The current app passed all 29 tests. A local smoke check ran two isolated app directories in separate processes using synthetic images and test PINs. Each accepted a photo, returned its own list, image and ZIP, and retained its photo across a fresh process. This verifies basic reuse of the current runtime and filesystem data. Provisioning and routing feasibility are supported by provider documentation. Live creation, routing, quota, restart, latency, failure recovery and teardown remain unmeasured. This review had no configured Fly credentials or staging zone and created no cloud resources.

### Cost model

Illustrative USD using Fly's public pricing effective 2026-10-01, a 720-hour month and European public egress at $0.02/GB. Rates vary by region. Model a 512 MB shared-cpu-2x event Machine at $0.0061/hour, a 5 GB event volume at $0.15/GB/month prorated, and 8 GB public egress per paid event including ZIP traffic. The 512 MB size and 8 GB traffic are assumptions to measure, and a 5 GB volume is a hosting allocation, not a customer quota. Same-region private gateway traffic is assumed free on granular billing. Model a permanent 512 MB gateway/demo service with 5 GB disk for both options. For shared paid events on Fly, add a permanent 1 GB shared-cpu-4x runtime and 20 GB volume. [Fly pricing update](https://fly.io/pricing-update/), [Fly resource pricing and network billing](https://fly.io/docs/about/pricing/).

| Estimated charge | Temporary Fly | Shared paid runtime on Fly |
| --- | ---: | ---: |
| Monthly gateway and demo baseline | $5.14 | $5.14 |
| Additional monthly paid capacity at idle | $0 if all resources are removed | $11.78 |
| Paid event, 24 h plus proposed 24 h host export window | $0.50 ($0.29 compute + $0.05 disk + $0.16 egress) | $0.16 egress while within provisioned capacity |
| Paid event, 72 h plus proposed 24 h host export window | $0.85 ($0.59 compute + $0.10 disk + $0.16 egress) | $0.16 egress while within provisioned capacity |
| Twenty paid events/month, half on each tier | $18.62/month | $20.12/month |

Without the export window, temporary event costs are about $0.33 and $0.67. At 50 GB of public egress, either option would incur $1.00 of bandwidth per event, $0.84 above the modeled case. Twenty-five guests browsing 2 GB of originals each can reach that range before exports. Measure display traffic and size browser renditions if full originals make bandwidth or latency unacceptable. Under the export-window assumptions, the added shared runtime and volume equal about 23 mixed events' worth of temporary compute and disk. That is a cost crossover only if the shared configuration handles the actual peak concurrency and disk footprint. A shared paid runtime on the existing host could have near-zero incremental fixed spend if suitable capacity, bandwidth, isolation and recovery are already in place. Measure that baseline independently. Budget for domain renewal, storefront/controller hosting if incremental, demo egress, monitoring, delivery email, recoverable backup copies, taxes and operator time. Orphaned volumes and stopped Machine root filesystems can accrue charges. Dedicated IPv4 and paid certificates are excluded from the example. Verify per-region pricing and account terms before committing to a launch budget.

Hosted Stripe Checkout is one candidate. Swedish standard EEA card pricing is 1.5% + SEK 1.80, about SEK 3.29 on 99 SEK and SEK 3.74 on 129 SEK. At a planning assumption of 10 SEK/USD, temporary infrastructure plus that card fee is about SEK 8.31 or SEK 12.19 per event, excluding monthly overhead and the other costs above. This is a contribution-cost estimate. Verify taxes, refunds, chargebacks, support effort and actual traffic before judging margins. A self-serve buy-to-ready path and reliable automatic cleanup matter more to the choice than the modeled compute difference at early volumes. [Stripe Sweden pricing](https://stripe.com/se/pricing), [Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment).

## Commercial blockers

| Priority | Finding | Required outcome |
| --- | --- | --- |
| Release blocker | `serve_upload` serves original files with public immutable caching even with VIEW_PIN. The ops notes also show a Caddy static shortcut. `/upload` has its own gate, and `/admin` renders without credentials. A Caddy example injects an upstream upload PIN. | Commercial media, listing, upload, moderation and export obey their role and event lifetime on every path. No direct origin or proxy bypass. Private or expiring content is never served from a public cache. Explicitly separate legacy demo/library deployment behavior. |
| Release blocker | The `/enter` redirect only checks a leading slash. Session signing can fall back to a PIN or a per-process random value. Admin PIN is kept in localStorage. PIN comparisons have no attempt limits. | Safe local redirects, stable independent signing secrets, secure host-only cookies, event/role binding, rotation/revocation, throttling and authenticated host actions. Keep secrets and identities out of URLs and logs except for a short-lived, single-use claim token if needed. |
| Release blocker | `_safe_name` can assign a JPEG suffix to arbitrary bytes. Multipart parsing precedes the file-length check. There is no pixel/frame ceiling, aggregate quota or bounded write path. | Edge and app request caps with multipart allowance, full decoded-format validation and image budgets, atomic publication, event byte/count limits, abuse protection and safe handling of original metadata and served MIME types. |
| Release blocker | `_metadb` and scan caches are process-local. Metadata writes are non-atomic and exceptions are suppressed. The sample service has four workers. ZIP requests perform full archive generation and lack cleanup on build failure. | Concurrent uploads, deletes and lists are consistent at production worker settings. Keep a single writer or use correct locking and atomic metadata updates. Bound ZIP jobs, disk usage and runtime. Record and clean interrupted work. |
| Release blocker | There is no separation of event credentials or storage, authenticated billing ledger, expiry authority, cleanup, alerting or recovery runbook. | Verify signed and idempotent checkout fulfillment, clock-controlled expiry, absence of provider resources and cached copies, safe restore during the agreed window, and an operator-visible status for every failed order or cleanup. |
| Before paid launch | Originals may carry GPS or other identifying metadata. Exported and guest-saved copies leave service control. Provider copies, logs and order data have separate retention needs. | Document retention and scope, decide whether to sanitize the browser rendition while retaining disclosed originals for host export, confirm processing terms, and exercise a deletion request and breach/refund workflow. [GDPR text, Articles 5 and 28](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng). |
