# Photowall commercial MVP implementation plan

The [MVP assessment](mvp-assessment.md) records the baseline, provider evidence, cost assumptions and launch blockers. The backlog below is ordered by dependencies and can be copied into issues as each change is scheduled. Start branches from current `main`, keep each PR focused, push it and report the exact test command and result.

## Product decisions to confirm before accepting money

| Decision | Proposed behavior for staging |
| --- | --- |
| Activation | The paid clock starts when the event first becomes ready after confirmed payment. Show absolute dates and times to the host. Stage both tiers using abbreviated timers. Future scheduled events can wait. |
| Expiry and export | At 24 h or 72 h, guest uploads and viewing end. A proposed 24 h host-only export grace period follows. Show the upload, viewing and deletion deadlines before purchase and in host handoff. Revoke access at the deletion deadline and target verified purge within one hour, subject to measured recovery and provider retention constraints. |
| Access | Paid guest access via event-specific viewer and upload credentials, with separate host access for moderation and export. Avoid account creation. Share a guest link without a secret and deliver the event-specific access codes separately. |
| Limits | Starting targets for the pilot are 250 photos and 2 GiB of original bytes per event, 25 simultaneous guests and at most one ZIP job per event. Keep the 10 MiB per-file limit. Measure headroom for staged uploads, ZIP creation and decoding at these limits. |
| Recovery and refunds | Propose at most 15 minutes of photo loss and recovery within 60 minutes during the paid window. Test these targets with a lost host or volume, and approve targets, retention and refund triggers before release. Confirm actual operating costs against both tier prices. |

These staging defaults are planning assumptions. Confirm the domain, availability and permissions of the storefront host, processor and tax/refund terms, photo recovery targets and deletion wording before the paid pilot.

## Staging comparison for MVP-03

The [local staging results](mvp03-staging.md) include the reproducible comparison and the outstanding live checks.

1. Build a reproducible pinned image. Use separately configured event data paths, a test-only gateway and one approved EU region. Record image digest, region, token scope, limits, boot and readiness times, and provider resource IDs in redacted logs.
2. Start two temporary Machines with encrypted volumes with automatic snapshots off. Route two test hostnames through one wildcard and gateway. Check edge/origin TLS, allowed Host handling, public-origin rejection and per-Machine routing for image requests, full multipart POSTs and ZIP downloads. Restart one Machine, then verify its photos remain available. Check repeat creation, interrupted provisioning, concurrent events and recovery after a lost create response using synthetic data.
3. Run the same two-event fixture on a shared runtime with separate filesystem roots and credentials. Verify isolation for lists, direct images, upload, delete and ZIP, including consistent handling of unsupported or unknown hosts. If shared tenancy requires substantial app code, scope the spike to a disposable harness and count the production work explicitly. Measure on the existing host only with its operator's approval, or use the equivalent measured Fly shared baseline.
4. Use the same workload for both candidates. Start with 25 guest clients per event, concurrent uploads including near-limit files, active wall and slideshow polling, a growing gallery up to 250 photos or 2 GiB, and a host ZIP. Record p50/p95 ready times and request latency, error rates, peak CPU/RSS/disk, transfer, restart recovery, and operator steps. Staging targets are p95 ready within 60 s over at least ten create cycles, a wall update within 20 s, and zero cross-event reads/writes or lost acknowledged uploads in the normal workload. Record the ZIP build time and accept it only if the chosen proxy path handles it within a tested timeout at quota.
5. Force expiry while traffic is active. Verify that the due event closes even if cleanup or the provider API stalls, that repeated cleanup succeeds, and that unrelated resources and traffic are unaffected. Confirm permanent removal of staging Machines and detached volumes from inventory, absence of snapshots, and the cost impact of unexpected leftovers. A paid recovery design must also cover host or disk loss and reconcile backup retention with deletion.
6. Choose temporary paid runtimes if routing and cleanup are automated, the recovery and workload targets have a credible measured path, and the operational and cost comparison favors them. Choose shared paid hosting if measured capacity, isolation and cleanup are adequate and it simplifies the service. Hold the paid launch if neither path meets the gates. Keep the checkout flow behind the ledger so the hosting choice stays reversible.

Use approved staging credentials and a recorded spending ceiling for live provisioning. A test run must start and finish with an inventory check for resources tagged to the run.
